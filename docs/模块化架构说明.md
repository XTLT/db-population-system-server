# 模块化架构说明

## 概述

本项目采用**完全模块化 + 一函数一文件**的架构：每个功能领域一个独立模块，模块内每个函数单独一个文件，最后由总调度文件统一导入组织。这种架构便于：

- **后期维护**：修改某个函数时，直接删除/重写对应文件，不影响其他模块
- **功能扩展**：新增功能只需添加新模块文件
- **代码复用**：模块间可共享工具函数
- **团队协作**：不同开发者可并行开发不同模块
- **冲突最小化**：文件粒度小，git 冲突概率低

> 注：本结构于 2026-09-27 重构完成。重构前的大单体文件（`web_app.py`、`database.py`、`utils.py` 等）已拆分归档/删除。

## 添加新模块

### 步骤

1. **创建模块包**：在 `api/` 下创建目录 `api/new_feature/`，新建 `__init__.py`：

```python
from flask import Blueprint

bp = Blueprint('new_feature', __name__)

from .get_new_feature import get_new_feature   # 每个函数一个文件
```

2. **每个函数一个文件**：如 `api/new_feature/get_new_feature.py`：

```python
from flask import jsonify
from utils.security import require_auth
from utils.response import safe_error


@bp.route('/new-feature')
@require_auth
def get_new_feature():
    """获取新功能数据"""
    # 业务逻辑
    return jsonify({'success': True})
```

3. **注册模块**：编辑 `api/__init__.py`：

```python
from .new_feature import bp as new_feature_bp

__all__ = [
    # ... 其他模块
    'new_feature_bp'
]
```

4. **注册蓝图**：编辑 `app_modular.py`，`app.register_blueprint(new_feature_bp, url_prefix='/api')`。

5. **测试**：

```bash
# 重启服务器
./start_server.sh restart

# 测试新端点
curl -k https://localhost:5000/api/new-feature
```

## 修改单个函数的流程

由于采用"一函数一文件"：

1. 定位函数文件（路径即模块 + 函数名，如 `server/database/functions/get_person_count.py`）
2. 删除该文件 → 新建同名的重写（或直接编辑）
3. 总调度 `__init__.py` 自动导入，无需改其他调用点（`from database import get_person_count` 不变）

## 与旧版对比

| 特性 | 旧版（拆分前） | 新版（当前） |
|------|--------------|------------|
| 文件数 | 大单体（web_app.py 3937 行、database.py 2218 行） | 639 个 .py 小文件 + 13 个 JS 模块 |
| 粒度 | 模块内多函数耦合 | 一函数一文件 |
| 维护 | 修改需理解大文件 | 直接替换单文件 |
| 扩展 | 修改大文件 | 添加新文件 |
| 冲突 | 多人改同一文件易冲突 | 文件粒度小，冲突少 |

## 最佳实践

1. **单一职责**：每个文件只写一个函数
2. **统一前缀**：模块内路由使用统一前缀
3. **权限检查**：使用 `@require_auth` 装饰器
4. **错误处理**：使用 `safe_error()` 统一错误响应
5. **会话管理**：使用 `get_session()` 并在 finally 中关闭
6. **不破坏 shim**：拆包后 `__init__.py` 的兼容导出不要随意删除
